# ADR 0005: RBAC — viewer / editor / fs-admin

## Статус

Accepted (MVP)

## Контекст

Нужна ролевая модель для админки кредитных продуктов. Помимо просмотра и редактирования требуется отдельная **роль админа для ФС** (фронтальная система / сопровождение ФС) с расширенными правами, в т.ч. на удаление продукта.

## Решение

Три роли в JWT (Keycloak client roles), наполняемые из AD-групп:

| Роль | Права |
|---|---|
| `credit-admin.viewer` | Чтение продуктов и аудита |
| `credit-admin.editor` | + создание и изменение продукта |
| `credit-admin.fs-admin` | + удаление продукта (soft-delete) и админские операции ФС |

Матрица:

| Действие | viewer | editor | fs-admin |
|---|---|---|---|
| GET products / audit | ✓ | ✓ | ✓ |
| POST create | | ✓ | ✓ |
| PATCH update | | ✓ | ✓ |
| DELETE (soft) | | | ✓ |

Удаление:

- Только soft-delete (`status=ARCHIVED` / `deleted_at`), чтобы сохранить историю и не ломать ссылочную целостность у потребителей.
- В `audit_events.operation = DELETE`.
- Hard delete из БД — вне scope (только DBA/ретеншн-процедуры).

Проверка прав — на API (resource server). UI скрывает кнопки по ролям, но не является границей безопасности.

## Последствия

(+) Явное разделение операционного редактора и админа ФС.  
(+) DELETE контролируется отдельно — ниже риск случайного вывода продукта.  
(+) Маппинг AD→роли остаётся у IAM/Keycloak.  
(−) Нужно договориться с владельцами ФС, кто входит в группу fs-admin.  
(−) Composite roles в Keycloak желательны, чтобы fs-admin автоматически включал права editor/viewer.
